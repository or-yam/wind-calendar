Backend flow map

Preferences arrive over HTTP; weather providers supply forecast data; the backend filters and selects sessions; an adapter returns JSON or calendar data. These routes store no user preferences and perform no calendar-account synchronization.

HTTP entry points

nitro.config.ts configures serverDir: ./server, the Vercel preset, and CORS for /api/**. Nitro filesystem routing maps the following files to URLs.

Call Flow Output / cache
GET /api/forecast Rate check → query config → sessions → JSON {meta, sessions}; public weather cache
GET /api/calendar Rate check → same config and sessions → ICS generation text/calendar; public weather cache
POST /api/interpret-config Method → flag → AI rate check → body validation → key → AI → schema validation {outcome, message, config}; no-store
GET /api/features Bulk flag evaluation; failure yields false values Three booleans; private, max-age=15
GET /api/health Local liveness response only {status, timestamp}; no-store

GET is the intended read flow. Forecast, calendar, and health files have no method suffix or explicit method restriction. Features is GET-only by filename; interpretation explicitly rejects non-POST with 405.

Caller differences

  • Browser app: JSON endpoint; browser enforces CORS. No authentication is required by these routes.
  • Native app, CLI, bot, service: same JSON contract. A shared outbound IP means a shared rate budget. Inspect HTTP status before parsing a success shape.
  • Calendar subscription: periodically retrieves the configured calendar URL. The server returns a feed, not a push notification. Vendor refresh behavior is outside this backend.
  • One-time calendar import: downloads a snapshot; these routes do not update the imported copy.
  • Monitoring: health checks show handler liveness, not end-to-end dependency readiness.

Input is a complete query configuration

Query conversion preserves repeated string values. Normalization adds defaults; parsing uses schemas and range checks.

Parameter Default Behavior
locations beit-yanai CSV and/or repeated values; trim and deduplicate; 1–3 known IDs. When present, overrides legacy singular location.
model om_gfs om_gfs / om_icon / om_gdps / om_ifs or 3 / 45 / 59 / 117
windEnabled, windMin, windMax true, 14, 35 Knots; min ≥ 0, max ≤ 200, min < max
waveEnabled, waveSource false, total Source is total or swell
waveHeightMin, waveHeightMax 0.5, 3 Meters; min ≥ 0, max ≤ 20, min < max
wavePeriodMin 0 Seconds; ≥ 0
minSessionHours 2 0–24 hours; applied after selecting locations

Only the exact query string true enables a supplied boolean. Omitted booleans take defaults. Numeric parsing uses parseFloat, so it is permissive about trailing text. Range validation runs even when the corresponding filter is disabled. Both filters disabled is accepted here and yields no sessions.

Location IDs, coordinates, Windguru spot IDs, and time zones live in shared/locations.ts. Arbitrary coordinates are not accepted by these routes. Model selection is shared across requested locations. There is no date/week input in the parser; extra query keys are ignored. 

# Substitute your deployment origin. Both URLs carry the same preferences.
curl -i 'https://YOUR_HOST/api/forecast?locations=beit-yanai,tel-aviv&model=om_icon&windMin=16&windMax=25'
curl -i 'https://YOUR_HOST/api/calendar?locations=beit-yanai,tel-aviv&model=om_icon&windMin=16&windMax=25'

Provider resolution and fallback

buildLocationSessions resolves locations concurrently using Effect.forEach. Each calls resolveForecastData. Required failure in any location fails the combined request; successful locations are not returned separately.

Requested model Primary model On Open-Meteo failure
om_gfs gfs_global Windguru 3
om_icon icon_global Windguru 45
om_gdps gem_global Windguru 59
om_ifs ecmwf_ifs025 Windguru 117

Numeric model IDs select Windguru directly. The fallback mapping is found by matching model names in shared/models.ts, not by a second hardcoded map.

Open-Meteo path

fetchForecast + fetchMarine request seven days, concurrently, with a 10-second timeout per HTTP request. Wind uses the chosen model and knots; marine is a separate API request without that wind-model selector. fetchOpenMeteoData converts local timestamp strings into UTC instants and merges wave/swell values by exact timestamp.

Marine request failures become an absent optional result; wind can continue. Failure of the required forecast or its normalization triggers provider fallback. Missing coordinates fails before this recovery path. A malformed marine payload that throws during merging is outside the optional HTTP failure boundary.

Windguru path

fetchWindData fetches the wind model and wave model 84 concurrently. getForecast first fetches spot metadata, checks model availability, extracts rundef, then fetches the forecast. Each upstream HTTP request has a 10-second timeout.

A failing non-GFS wind-model fetch gets another attempt using GFS 3. A failing GFS fetch is terminal. Wave-fetch failure is optional. Wave merging supplies total height only; period, direction, and swell remain null. Consequently, a positive required wave period or swell-only criteria may eliminate every wave match after fallback.

Fallbacks are recovery choices, not a general retry loop. The 10-second timeout is per upstream request, not a whole-request time limit. Wave requests happen even when wave filtering is disabled.

How weather becomes sessions

  1. Normalize: both adapters produce ProviderWindData: dated wind/wave/swell points plus sunrise and sunset strings.
  2. Filter: filterEvents removes past points and points outside daylight. An enabled wind criterion OR enabled wave criterion must pass. Heights and wind ranges are inclusive; wave period must meet its minimum. Missing period is treated as zero. Each surviving point gets wind, wave, or both.
  3. Group provisional candidates: groupSessions sorts points; changes of match type or gaps above three hours split a group. Here minimum duration is zero.
  4. Pick winners: selectBestLocationSessions gathers candidates with identical timestamps. Wind speed wins first if wind is enabled; wave height wins next if waves are enabled, using the configured total/swell source. A criterion a candidate did not pass ranks as −1. Remaining ties use requested location order.
  5. Regroup: winner runs split when location or match type changes, then grouping applies temporal gap rules. End = last point + last step, or one hour for a singleton. Drop sessions shorter than minSessionHours. Compute summaries over retained points.

Selection is greedy per timestamp; it does not maximize total usable time. A short winning run may be removed by the duration rule without reinstating a runner-up location. Comparison is by exact sample timestamp, not arbitrary overlapping time intervals. The JSON field hourly can contain three-hourly samples.

Same sessions, two output formats

JSON: ForecastResponse has meta (requested model, requested locations, generation timestamp, provider per location) and sessions. Dates are ISO UTC strings. Session summaries round values; raw time-point fields preserve nulls. Some missing aggregate values become zero or direction N, so inspect raw data when absence matters.

ICS: generateIcsEvents creates UTC events with titles, location text, and locally formatted condition descriptions. UID = version + encoded location ID + start milliseconds + end milliseconds + domain. Unchanged boundaries keep identity; changed boundaries generate a new UID. Vendor reconciliation is not established here. RFC 5545 UID semantics.

Successful JSON/ICS use Cache-Control: public, max-age=21600, stale-while-revalidate=86400, stale-if-error=604800: six-hour freshness, plus advertised stale handling windows. Actual reuse depends on the client/intermediary. These handlers contain no persistent weather cache; an origin request executes the pipeline again. Cached JSON's generatedAt describes generation time, not retrieval time.

X-Data-Source lists actual providers (openmeteo, windguru); JSON also maps provider by location. X-Fallback-Used: true reports Open-Meteo → Windguru fallback, but not Windguru's internal GFS fallback. meta.model stays the requested model, so metadata does not establish the actual final model.

Failures and request tracing

observedHandler assigns X-Request-Id, creates request logging context, logs completion or failure and duration, and preserves request ID and Retry-After on errors. Forecast, calendar, features, and interpretation use it; health does not. runLoggedEffect connects Effect logs to structured JSON request logs.

HTTP helpers create typed provider errors. Error classification converts them to ForecastError; toHttpError translates pipeline failures for Nitro. Configuration errors become 400. Unrecovered timeout/network errors generally become 504; upstream bad responses generally become 502; upstream throttling can become 429. Windguru wraps some model-fetch failures as data errors, which can lose the original HTTP classification. Unexpected defects become 500.

HTTP errors are serialized by Nitro/H3; custom error details are in data in the integration fixtures. Do not assume a failed response has the success JSON shape, or that a calendar failure returns ICS. A successful sessions: [] or empty VCALENDAR means no retained matches, not necessarily a provider outage. JSON fixtures · ICS fixtures.

Rate limiting allows 30 requests per rolling minute per IP in a process-local map. Forecast and calendar share the IP bucket; interpretation uses a separate ai:IP bucket with the same limit. Features and health do not call the limiter. This is best-effort across serverless instances, not a globally enforced quota. IP comes from the first X-Forwarded-For value, then the socket address, then unknown; deployment proxy behavior matters.

Implementation details worth remembering

  • Daylight: Open-Meteo uses the first day's sunrise/sunset for the whole horizon; filtering compares only the integer local hour. Minute boundaries and changing daily daylight are approximations. Time helpers.
  • DST: Open-Meteo conversion applies one returned UTC offset to every point. A horizon spanning an offset transition deserves scrutiny.
  • Validation differs: AI output uses a strict Zod schema requiring at least one filter enabled; query parsing allows both disabled. Query numeric parsing is more permissive.
  • Flags: flag evaluation defaults to false on failure. Only the AI route enforces a flag; wave/model capability flags do not restrict forecast/calendar callers.
  • Malformed data: some provider shapes are asserted rather than fully decoded. Windguru missing WINDSPD can log a warning and return an empty array; not every bad payload becomes a clean provider error.
  • Old code: server/open-meteo/config.ts is not the parser used by current routes. Follow imports from the entry point before trusting a file's descriptive comments.
